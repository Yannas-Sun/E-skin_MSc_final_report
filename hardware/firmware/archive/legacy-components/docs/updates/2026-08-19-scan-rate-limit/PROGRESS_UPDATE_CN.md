# 扫描频率限制分析：为什么当前 STM32 链路无法达到 700 Hz

日期：2026-08-19  
范围：分析当前系统的时序、ADC 时钟限制、传输开销、原版 Teensy 直连扫描与当前 STM32 + Teensy 架构的差异，并记录四模块传输的当前状态和后续路线。

状态：**当前 STM32 完整扫描链路尚未达到 700 Hz。** 原版 Teensy 直连架构在一次 10 秒传输测试中达到了 700.210 个完整帧/秒，但它使用了不同的时序路径，且仍需要进一步进行受控压力和模拟信号验证。当前四模块桥接、固定 `MUL1` 数据包、解析器和模块化模拟器页面已经实现；下一步需要让四模块链路具备更好的自适应能力、故障识别能力和带宽效率。

## 1. “700 Hz”具体代表什么

对于一个完整模块帧，700 Hz 表示每隔以下时间产生一帧新的双 FSR + 九个 ACC 数据：

```text
1 / 700 = 1,428.6 微秒
```

这并不只是一次 FSR 扫描。每个周期还必须包括：

- 16 个 MUX 地址；
- 两个 16 通道 ADC；
- MUX 稳定时间；
- 9 个加速度计；
- 数据打包；
- CRC 或状态处理；
- Host SPI 握手；
- STM32 到 Teensy 的数据传输。

如果要求四个模块中的每个模块都达到 700 Hz，则共享 Host SPI 总线需要处理 2,800 个完整模块帧/秒。这与“700 个四模块聚合包/秒”是两个不同、且难度更高的目标。

## 2. 当前实测基线

当前维护的 Combined 固件由 STM32 完成完整采集，Teensy 只负责 Host SPI 主机和 USB 桥接。已经记录的完整扫描结果如下：

| 配置 | 完整帧频率 | 数据质量结果 |
|---|---:|---|
| 当前稳定 Combined 固件 | **238.475 帧/秒** | 传输有效，但 FSR 新鲜数据频率远低于 700 Hz |
| SCLK33，2.5 MHz | 205.444 帧/秒 | ADC 数据质量通过基线测试 |
| SCLK33，7.5 MHz | **439.299 帧/秒** | 传输和质量窗口通过，但超过 ADC 规格 |
| SCLK33，10 MHz，STM32 160 MHz | 581.667 帧/秒 | CRC/传输通过，但出现 ADC 位边界失真 |
| 原版 Teensy 直连扫描 | **700.210 帧/秒** | 传输通过，但仍需模拟压力响应验证 |

7.5 MHz 和 10 MHz 的 SCLK33 结果属于诊断性实验，不能作为符合器件规格的生产配置。当前稳定版本仍明显低于 700 Hz 目标。

## 3. ADC 外部 SCLK 的最低要求

复刻的 33 字节事务中，每个 ADC、每个 MUX 地址需要传输 33 字节。完整双 FSR 扫描需要：

```text
2 个 ADC × 16 个地址 × 33 字节 = 1,056 字节
```

仅计算 SPI 线上传输时间：

| ADC 外部 SCLK | 仅 FSR 线传输时间 |
|---:|---:|
| 10 MHz | 844.8 微秒 |
| 7.5 MHz | 1,126.4 微秒 |
| 4.8 MHz | 1,760.0 微秒 |

MAX11633 的外部转换 SCLK 规格上限为 4.8 MHz。若仅希望让 FSR 字节传输本身达到 700 Hz，需要：

```text
1,056 × 8 × 700 = 5.9136 MHz
```

这个数值已经超过 4.8 MHz 的外部转换时钟上限，而且还没有为 MUX 稳定、ACC、数据打包和 Host SPI 留出时间。因此，复刻实验中的 10 MHz 是超规格实验。需要特别区分：正常内部转换的 Combined 链路中的 SPI 读取时钟，与 SCLK33 外部转换时钟不是同一个概念。

## 4. Host SPI 时间预算

一个完整的 `ESK1` 帧为 1,188 字节。当前 Host SPI 为 10 MHz 时：

```text
1,188 × 8 / 10 MHz = 每个模块帧 950.4 微秒
```

在 700 Hz 下，一个周期只有 1,428.6 微秒，因此 Host SPI 传输后只剩约 478.2 微秒，供 STM32 完成双 FSR 采集、ACC 读取、数据打包以及 IRQ/NSS 管理。当前采集阶段已经超过这个剩余预算。

对于共享同一 Host SPI 的四个模块，仅传输四个模块帧就需要：

```text
4 × 950.4 微秒 = 3.80 毫秒
```

这还没有计算采集和调度开销。因此，当前单条 10 MHz Host SPI 链路无法让四个模块都完成 700 Hz 的完整更新。

## 5. 原版 Teensy 直连代码为什么更快

已验证的原版测试使用 `ESKIN_ORIGINAL_700HZ.ino`，其关键路径与当前系统不同：

1. Teensy 直接控制 MUX 和两个 ADC。
2. ADC 转换和结果读取使用一次连续的 Mode-0 SPI 事务。
3. 不轮询 EOC。
4. 不插入显式 MUX 稳定延时。
5. 没有 STM32 采集、打包和 Host SPI 中转环节。
6. 固定长度的 1,132 字节帧直接从 Teensy 发往 USB。

这说明，即使 MUX 和 ADC 的型号完全相同，不同固件架构也不会自动得到相同的频率。原版测试证明直连架构可以满足时序目标，但不能证明当前 STM32 链路在保持相同模拟信号质量和协议可靠性的情况下也能达到 700 Hz。原版无压力测试中的 FSR 原始范围只有 0..29，因此还需要验证受控压力响应、串扰、行列映射和长时间模拟稳定性。

## 6. 为什么目前的优化仍然不够

当前固件已经使用了多项优化：

- 尽可能重叠 ADC 转换阶段；
- 在 SCLK33 实验中使用 SPI1 DMA；
- Host SPI3 使用 DMA 和乒乓缓冲；
- 对数据打包和 USB 队列进行流水化；
- 尝试周期性 CRC 检查。

这些优化可以减少 CPU 阻塞，但无法消除以下固定成本：ADC 的物理 SCLK 时间、MUX/模拟电路稳定时间、串行 Host SPI 线传输时间以及九个 ACC 的事务开销。160 MHz 实验将 FSR 阶段降低到约 1,426 微秒，但这几乎已经占满 1,428.6 微秒的 700 Hz 周期，还没有计算约 159 微秒的 ACC 阶段和约 53 微秒的数据打包阶段。该实验的 ADC 数据质量仍未通过，尽管采样到的网络 CRC 错误为零。

## 7. 四模块目前已经实现的功能

当前四模块实现是在原有单模块 `ESK1` 帧之上增加传输和可视化层。它并不声称四个模块都可以各自以 700 Hz 产生新的完整扫描。

### 7.1 共享 SPI 的 Teensy 桥接

当前四模块 Teensy 固件已经实现：

- 四组独立的 `HOST_nCS` 和 `HOST_IRQ` 插槽；
- 四个模块共享 Host SPI 的 SCK、MOSI 和 MISO，只有被选中的 CS 可以驱动 MISO；
- 按 Module 0 到 Module 3 进行轮询；
- 每个模块独立统计序号、CRC、超时、坏帧和 IRQ 释放超时；
- 使用 10 MHz、Mode-0 Host SPI 读取 STM32 帧；
- 使用小型 USB 发送队列，避免 USB 发送时覆盖下一组数据；
- 100 ms 部分轮次超时，使一个缺失或过慢的模块不会无限期阻塞其余模块；
- 使用 `updatedMask` 标记当前外层数据包中哪些模块提供了新帧。

针脚分配和烧录指令记录在 [四模块通信报告](../2026-08-18-four-module-communication/PROGRESS_UPDATE.md) 和 [scalablity/README.md](../../../teensy/applications/scalablity/README.md) 中。

### 7.2 `MUL1` 多模块数据包

当前外层数据包固定为四个模块槽位：

```text
MUL1 头部（20 字节）
+ 4 ×（模块 ID + 状态 + 保留字段 + 1,188 字节 ESK1 帧）
+ 外层 CRC32（4 字节）
= 4,792 字节
```

这样可以保证主机端具有稳定的数据包边界，同时保留每个模块独立的内部序号和时间戳。即使只有部分模块更新，其他模块的有效帧也可以继续发送，便于故障隔离和可扩展性测试。

### 7.3 解析器和四模块 GUI

软件模拟器集成已经支持：

- 严格检查 `MUL1` magic、版本、模块数量、数据长度和块长度；
- 先验证外层 CRC32，再验证每个模块内部的 `ESK1`；
- 重建每个模块的 FSR1 和 FSR2 矩阵；
- 重建每个模块的 9 个 ACC 记录；
- 查看所有模块，或只查看 Module 0–3 中的一个模块；
- `FSR + ACC`、`FSR only` 和 `ACC only` 三种视图；
- 显示数据包 FPS、USB 比特率、数据包序号、CRC 错误和解析错误；
- 使用独立的四模块实时页面，不影响原有单模块实时页面。

当前页面为：[multi-module-live.html](../../../software-simulation/frontend/multi-module-live.html)。

### 7.4 当前实现已经证明的内容

当前实现证明了：在共享 SPI 拓扑中，四个模块可以被独立识别、封装、解析和路由；同时也具备进行下一阶段测试所需的基础监控能力，包括每模块公平性、`updatedMask` 行为、队列压力、CRC/序号完整性以及 GUI 故障显示。

但是，当前实现还没有证明四模块可以完成 700 Hz 的完整轮次，也没有解决模块断开后继续显示旧帧的问题。

## 8. 一次完整扫描和跨设备传输流程

下面以当前四模块 `MUL1` 桥接模式为例，描述一轮完整的数据流。单模块模式使用相同的 STM32 `ESK1` 内部帧，只是没有四模块外层聚合。四模块的一轮并不是四个模块在同一个时刻严格同步采样，而是 Teensy 依次读取各模块最近准备好的有效帧，再将它们封装到一个 `MUL1` 数据包中。

### 8.1 STM32 启动和准备

每个模块上的 STM32G474 独立执行以下初始化：

1. 初始化系统时钟、GPIO、DMA、FSR ADC SPI1、ACC SPI2 和 Host SPI3。
2. 配置两个 MAX11633 ADC 和 MUX 控制线。
3. 初始化九个 ACC，并读取 `WHO_AM_I`、写入控制寄存器，再读回确认配置。
4. 将 `HOST_IRQ` 初始化为低电平，避免 Teensy 在数据尚未准备好时开始读取。
5. 进入 `CombinedAcquisition_RunOnce()` 的无限循环。

STM32 的主循环不是由 PC 逐帧请求触发的，而是持续准备下一帧。这样 Host SPI 读取和下一帧传感器采集可以流水执行。

### 8.2 STM32 扫描一帧 FSR

一次完整 FSR 扫描包含两个 16×16 阵列的全部 16 个 MUX 地址：

1. 设置四根 MUX 地址线，选择当前行。
2. 同时使能两个 FSR MUX，并等待模拟信号稳定。
3. 分别向 ADC1 和 ADC2 发送 16 通道扫描启动命令。
4. 轮询两个 ADC 的 EOC，直到两个转换阶段完成。
5. 关闭当前 MUX，并立即选择下一行，使下一行开始稳定。
6. 在下一行稳定的同时，依次读取 ADC1 和 ADC2 的 32 字节 FIFO 数据。
7. 将 16 个 12-bit ADC 结果写入 FSR1；将 FSR2 进行既定的反向/转置映射后写入第二个矩阵。
8. 重复上述过程，直到 16 个地址全部完成。

当前稳定 Combined 路径使用“下一行 MUX 稳定”和“上一行 ADC FIFO 读取”重叠的流水方式，但两个 ADC 的 FIFO 读取仍然共享 SPI1 MISO，不能同时进行数字读取。

### 8.3 STM32 读取 ACC

FSR 扫描后，STM32 执行 `scan_acc()`：

1. 只有到达 ACC 更新周期时，才读取 ACC 样本。
2. 对每个已初始化的 ACC 设置地址线并使能对应的片选。
3. 通过 SPI2 连续读取 X、Y、Z 六个输出字节。
4. 检查读取结果是否为全 0 或全 `0xFF`，并记录状态。
5. 每约 100 ms 只轮询一个 ACC 的 `WHO_AM_I`，逐步覆盖九个器件，避免每帧都重复执行九次身份检查。

因此，ACC 的物理更新频率、ACC 总线读取频率和完整输出帧频率不是完全相同的概念。帧中会携带 ACC 当前缓存值以及有效/错误状态。

### 8.4 STM32 生成 `ESK1` 帧

STM32 将当前采集结果按固定格式写入 1,188 字节的 `ESK1` 帧：

```text
4 B     ESK1 magic
1 B     协议版本
1 B     状态/新鲜度标志
2 B     帧长度（1,188）
4 B     STM32 帧序号
4 B     STM32 时间戳
512 B   FSR1（16×16，uint16）
512 B   FSR2（16×16，uint16）
144 B   9 个 ACC 记录，每个 16 B
4 B     CRC32 或非 CRC 周期的零尾部
```

当前协议版本 2 按固定周期携带 CRC32，其余帧使用零尾部；Teensy 和 PC 都会根据版本、标志位和序号判断该帧是否应该检查 CRC。

### 8.5 STM32 的 Host SPI DMA 和 `HOST_IRQ`

STM32 使用两个 Host SPI 缓冲区进行乒乓传输：

1. 首次运行时先完整采集并填充第一块发送缓冲区。
2. STM32 等待上一次 Host SPI 的 NSS 释放，重新初始化必要的 SPI 状态。
3. 为 SPI3 同时开启 TX/RX DMA，保证 MISO 发送和 MOSI dummy 字节接收都已准备好。
4. STM32 将 `HOST_IRQ` 拉高，通知 Teensy“当前模块已有完整 `ESK1` 帧可以读取”。
5. Teensy 进行 Host SPI 读取的同时，STM32 CPU 在另一块缓冲区中采集 FSR、读取 ACC 并打包下一帧。
6. SPI3 DMA 完成后，STM32 的 DMA 回调记录完成状态，并将 `HOST_IRQ` 拉低。
7. 两个缓冲区交换所有权，下一次传输发送刚刚准备好的新帧。

如果 Host SPI 超时或发生错误，STM32 会拉低 `HOST_IRQ`、停止 DMA、重新初始化 SPI3，并在短暂延时后重新进入循环。

### 8.6 Teensy 读取一个 STM32 模块

四模块 Teensy 桥接在循环中检查四根独立的 IRQ：

1. 依次检查 Module 0、1、2、3 的 `HOST_IRQ`。
2. 如果 IRQ 为低，说明该模块暂时没有新帧，Teensy 立即跳过它。
3. 如果 IRQ 为高，Teensy等待约 50 微秒，然后将该模块的专用 CS 拉低。
4. Teensy 使用 10 MHz、Mode-0 Host SPI 发送 dummy 字节并读取数据。
5. 先在最多 8 个字节内寻找 `ESK1` magic，完成同步后读取剩余帧内容。
6. 将 CS 保持约 10 微秒后拉高，结束该模块的 SPI 事务。
7. 检查帧版本、声明长度、CRC 尾部、内部序号和 magic。
8. 有效帧写入该模块的缓存，并更新该模块的成功计数和序号计数。
9. Teensy等待该模块的 IRQ 回到低电平；正常情况下很快完成，异常时最多等待 100 ms。

一个没有连接的模块若 IRQ 由下拉保持低电平，会在第 2 步直接被跳过；它不会阻塞其他模块。若 IRQ 错误地保持高电平，则可能进入 SPI 读取和最长 100 ms 的 IRQ 释放等待。

### 8.7 Teensy 组装 `MUL1` 外层数据包

每当一个或多个模块成功更新，Teensy 会将对应位加入 `pendingUpdateMask`。满足以下任一条件时，Teensy 组装一个外层数据包：

- 四个模块全部更新；
- 已经有模块更新，但等待时间达到 100 ms 的部分轮次超时。

`MUL1` 数据包组装过程为：

1. 写入 `MUL1` magic、版本、模块数量、更新掩码、包长度和块长度。
2. 写入外层数据包序号和 Teensy 时间戳。
3. 按 Module 0 到 Module 3 写入四个固定模块块。
4. 每个块包含模块 ID、状态、保留字段和该模块最近一次有效的 1,188 字节 `ESK1` 帧。
5. 对除尾部外的整个数据包计算外层 CRC32。
6. 将 4,792 字节数据包放入 Teensy 的 USB 队列。

因此，`updatedMask` 表示本次外层包中哪些模块真的提供了新帧；其他模块可能是等待中、错误状态，或仍保留上一帧数据。

### 8.8 Teensy 通过 USB 发送到 PC

Teensy 不会一次强制写出整个 4,792 字节，而是：

1. 检查 USB `availableForWrite()` 空间。
2. 按当前可用空间分块调用 `Serial.write()`。
3. 记录当前包已经发送的偏移量。
4. 当前包全部发完后，释放队列槽位并开始发送下一个包。

这使 SPI 读取、数据包组装和 USB 发送可以部分重叠，但 USB 队列仍然可能因为主机读取不及时而达到高水位或溢出。

### 8.9 PC 后端接收和解析

用户在四模块 GUI 中点击 `Start live` 后，浏览器每约 80 ms 向后端发送一次：

```text
POST /api/mul1-frame
{
  "port": "COM9",
  "baud": 2000000
}
```

PC 后端的过程为：

1. 通过 PySerial 打开 Teensy 的 COM 端口，并清空输入缓存。
2. 创建后台串口读取线程，避免 HTTP 请求阻塞在串口读取上。
3. 连续读取字节，直到找到 `MUL1` magic。
4. 读取固定长度的外层头部，检查声明的数据包长度是否为 4,792 字节。
5. 继续读取完整数据包，并验证外层 CRC32。
6. 按四个固定块解析模块 ID、模块状态和内部 `ESK1` 帧。
7. 对状态为有效的模块再次验证内部 magic、版本、长度、CRC 和 16×16/ACC 数据范围。
8. 将最新数据缓存为 JSON，并计算数据包 FPS、串口字节率和错误计数。
9. 如果出现超时或 CRC/解析错误，保留错误计数并重新寻找下一个 `MUL1` 边界。

### 8.10 GUI 显示

浏览器收到后端 JSON 后：

1. 更新总状态、Packet FPS、USB rate、Packet sequence 和 CRC/parse errors。
2. 根据模块选择器显示全部模块或指定模块。
3. 根据视图选择器显示 FSR、ACC 或 FSR + ACC。
4. 将每个模块的 FSR1/FSR2 16×16 数组绘制成独立热力图。
5. 将该模块的九个 ACC 记录绘制在对应卡片中。
6. 如果模块没有有效帧，显示等待/状态信息；当前版本对于“曾经有效后再断开”的模块仍需要增加数据年龄判断，避免把旧帧长期显示为新鲜数据。

完整链路可以概括为：

```text
FSR/ACC 传感器
    ↓
STM32 MUX/ADC/ACC 扫描
    ↓
STM32 生成 ESK1，并通过 HOST_IRQ 通知
    ↓
Teensy 用专用 CS + Host SPI 读取 ESK1
    ↓
Teensy 聚合四个模块为 MUL1，并计算外层 CRC32
    ↓
Teensy USB Serial 分块发送
    ↓
PC PySerial 后台线程
    ↓
MUL1/ESK1 解析、CRC、序号和状态检查
    ↓
JSON 缓存和 80 ms GUI 轮询
    ↓
四个模块的 FSR 热力图和 ACC 数据
```

## 9. 软件模拟器中可参考的扫描和传输策略

复制到当前项目的软件模拟器已经实现了多种可供固件后续参考的策略。这些策略目前是算法参考，并不表示它们已经运行在 STM32 实物板上。具体参考文档为：[software-simulation/docs/FIRMWARE_ALGORITHMS.md](../../../software-simulation/docs/FIRMWARE_ALGORITHMS.md)。

### 8.1 基于时间的稀疏完整帧模式

模拟器的 Combined 模式在空闲时使用低频率（10 Hz），通过 Tare 或基线进行比较；当压力超过阈值时切换到指定的高速频率；压力消失约一秒后回到低频率。这样可以在触摸发生时保持完整帧格式，同时降低平均带宽和功耗。

四模块可采用的方式：

- 为每个模块保持低频健康检查和心跳扫描；
- 只有 Sentinel 值超过阈值的模块进入高频扫描；
- 被触发的模块仍发送普通完整 `ESK1` 帧；
- 在 `MUL1` 状态字段中加入每模块扫描模式和数据新鲜度。

### 8.2 Delta 变化量传输

模拟器的 Delta 策略会周期性发送完整同步帧，在其余帧中只发送相对于基线变化超过死区的 FSR 单元。当前参考阈值为 8 个 ADC 码，接收端负责重建完整矩阵。

未来可以增加类似 `MUL1D` 的外层数据包：

```text
MUL1D 头部
+ 模块 ID、基准序号、变化数量
+（层、行、列、数值）记录
+ 周期性完整帧检查点
+ 外层 CRC32
```

这种方法在大部分 FSR 单元静止时可以明显降低 USB 流量，但接收端必须为每个模块保存状态，并且必须设计完整检查点、丢包恢复和数据过期机制。

### 8.3 空间稀疏扫描

模拟器的空间稀疏策略在空闲时保持六条 Sentinel 行/列工作，使用的 1-based 行/列为 2、5、7、10、12、15。当检测到压力点时，打开该点附近的 3×3 邻域；多个压力点的邻域通过掩码并集合并；最后一个压力点消失后，邻域保持约一秒，以确保释放过程仍能被传输。

对应的稀疏传输格式为：

- `ESP0`：短的空闲/无变化数据包；
- `ESPD`：当前扫描掩码中变化的点；
- `ESPF`：周期性发送扫描掩码和相对于基线的当前值，用于同步。

该策略最有潜力减少当前 16 行 FSR 扫描的成本，但必须先在真实硬件上验证 MUX 稳定时间、串扰、很小的接触区域是否会漏检以及压力释放过程。

### 8.4 FSR 和 ACC 独立频率

软件模拟器和 SCLK33 实验都支持独立设置 FSR 与 ACC 的刷新目标。因此未来可以让 FSR 使用较高频率，而 ACC 使用较低更新率，同时保持一个固定输出外层格式。接收端必须提供数据新鲜度标志，不能把保留的 ACC 样本误认为当前刚刚采集的新样本。

### 8.5 Patch 聚合和吞吐量计算

软件模拟器已经支持任意模块布局、Patch 分组和根据模块数量及采样频率计算吞吐量。这可以成为硬件调度器的规划工具：在烧录前选择需要工作的模块，预先计算总数据量和 USB 速率，并拒绝超出共享 Host SPI 能力的请求。

## 10. 后续需要继续添加的功能

下一阶段应按照“先保证数据正确，再提高速率”的顺序进行。

### 优先级 1：数据新鲜度和故障状态

1. 在 `MUL1` 中增加每个模块的 `last_valid_ms` 或数据年龄字段。
2. 模块连续若干次未更新后，将之前有效的模块标记为过期或离线，不能继续显示为 `valid`。
3. GUI 区分 `fresh`、`stale`、`waiting`、`CRC error` 和 `timeout` 状态。
4. 增加断开、重新连接和复位单个模块的恢复测试，确认其他三个模块不会停止或重新编号。

### 优先级 2：自适应四模块调度

1. 用每模块独立调度器替换固定轮询假设，并记录实际截止时间。
2. 为不同模块支持独立 FSR 和 ACC 更新频率。
3. 对非活动模块保留低频健康检查，把更多总线时间分配给有新 IRQ 或有触摸触发的模块。
4. 在诊断流中记录每模块频率、公平性、扫描年龄和 Host SPI 利用率。

### 优先级 3：带宽感知的数据包格式

1. 实现带周期性完整检查点的 `MUL1D` Delta 外层数据包。
2. 实现基于 Sentinel 行/列和 3×3 掩码并集的 `MUL1S` 空间稀疏外层数据包。
3. 增加协议版本协商或明确的桥接模式，使旧 `ESK1` 接收端仍能工作。
4. 定义 Delta 或稀疏数据包丢失后的重新同步流程，下一次完整检查点必须能恢复模块状态，不能要求重启 Teensy 或 GUI。

### 优先级 4：稀疏算法的真实硬件验证

先在一个模块上验证，再扩展到四个模块。需要测量：

- Sentinel 行/列之间是否会漏掉小接触点；
- 新压力点出现在当前掩码之外时的响应延迟；
- 相邻行/列串扰；
- 压力释放和迟滞；
- FSR 数据质量指标和 ACC 数据新鲜度；
- Host SPI、USB 和功耗是否真实下降。

只有当这些测试通过后，才能把稀疏扫描称为更高的“事件响应频率”。不能把它报告成 700 Hz 的完整 16×16 矩阵刷新率。

### 优先级 5：扩展到四个以上模块

当前数据包和解析器故意固定为四个模块。若要支持第五个或更多模块，需要增加模块数量/能力字段、可变长度或分段数据包、动态 CS/IRQ 配置以及 GUI 模块注册表。将第五个模块接到未配置的引脚上，当前桥接不会自动发现它。

## 11. 更新后的路线和验收规则

下一阶段建议按以下顺序执行：

1. 完成四模块数据新鲜度和离线状态修复，并在模拟器中使用合成 `MUL1` 数据包进行回放测试。
2. 使用当前完整帧模式，以 100、150 和 200 Hz/模块进行四模块速率扫描，同时记录功耗和队列状态。
3. 实现一个 Delta 或空间稀疏 `MUL1` 原型，并先完成解析器测试。
4. 在受控压力条件下，先对一个模块验证该原型。
5. 逐步扩展到两个、三个和四个模块，测量数据量、公平性、功耗、温度、CRC 和恢复时间。
6. 在软件模拟器和真实硬件原始数据捕获之间比较完整帧模式与稀疏模式。

最终验收规则保持不变：一种模式只有在其声明的扫描语义、ADC 数据质量、CRC/序号完整性、公平性、功耗预算和故障恢复全部通过后，才算成功。仅仅减少数据包大小或提高 GUI 刷新率，不能证明完成了 700 Hz 的完整 16×16 扫描。
