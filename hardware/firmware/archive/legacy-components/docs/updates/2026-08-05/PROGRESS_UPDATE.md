# E-SKIN Progress Update — 5 August 2026

> Historical report. The current measured performance and ordered optimisation
> workflow are in the [10 August 2026 update](../2026-08-10/PROGRESS_UPDATE.md).

## Executive summary

The first complete E-SKIN module is now operational as one end-to-end system:

```text
Two 16 × 16 FSR arrays + nine ACC positions
                    ↓
               STM32G474
                    ↓  Host SPI + IRQ, fixed binary frame, CRC32
               Teensy 4.1
                    ↓  USB CDC
                 PC GUI
```

The STM32 scans both pressure arrays and the accelerometer bus, builds one
versioned frame, and sends it to a Teensy 4.1. The Teensy validates the complete
frame before forwarding it to the PC. The GUI can display **FSR1**, **FSR2**,
**ACC**, or **all sensors together**. The complete single-module path has been
demonstrated successfully.

> 中文讲解：目前一个完整模块已经打通：两个FSR、ACC、STM32、Teensy和电脑GUI可以作为一个系统工作。

## 2. Communication principle

### 2.1 Sensor acquisition

The STM32 is the acquisition controller.

- **FSR1 and FSR2:** four MUX address lines select one of sixteen positions.
  After analogue settling, ADC1 and ADC2 each scan AIN0–AIN15. Each array
  therefore produces 256 unsigned 12-bit values in the range `0..4095`.
- **ACC array:** nine LIS2DH12 devices share SCK, MOSI and MISO. A decoder selects
  one active-low nCS output. XYZ data are read every acquisition cycle; identity
  and recovery checks are distributed periodically to reduce repeated traffic.

The established physical mappings are retained:

```text
FSR1: logical data derived from [MUX1][ADC1]
FSR2: reverse MUX2 selection plus transpose into the logical display map
ACC : decoder indices 0..8 correspond to physical A1..A9
```

### 2.2 STM32-to-Teensy Host SPI

The Teensy is the SPI master; the STM32 is the SPI3 slave.

| Signal | STM32 | Teensy 4.1 | Function |
|---|---|---|---|
| HOST_IRQ | PB8 | GPIO2 | STM32 indicates a ready frame |
| nCS/NSS | PA15 | GPIO10 | Teensy selects the STM32 slave |
| MOSI | PB5 | GPIO11 | Teensy dummy/control bytes to STM32 |
| MISO | PB4 | GPIO12 | STM32 frame bytes to Teensy |
| SCK | PB3 | GPIO13 | Clock generated by Teensy |
| GND | GND | GND | Common reference |

Transaction sequence:

```text
1. STM32 completes sensor acquisition.
2. STM32 packs the frame and calculates CRC32.
3. STM32 asserts HOST_IRQ.
4. Teensy pulls nCS low and provides SCK.
5. STM32 shifts the complete frame on MISO.
6. Teensy releases nCS; STM32 releases HOST_IRQ.
7. Teensy validates magic, version, length and CRC32.
8. Only a valid frame is forwarded over USB.
```

### 2.3 Combined frame format

| Offset | Size | Content |
|---:|---:|---|
| 0 | 4 B | Magic `ESK1` (`45 53 4B 31`) |
| 4 | 1 B | Protocol version |
| 5 | 1 B | FSR1 / FSR2 / ACC status flags |
| 6 | 2 B | Declared frame length: 1188 B |
| 8 | 4 B | Frame sequence number |
| 12 | 4 B | STM32 millisecond timestamp |
| 16 | 512 B | FSR1: 256 × uint16 |
| 528 | 512 B | FSR2: 256 × uint16 |
| 1040 | 144 B | Nine 16-byte ACC records |
| 1184 | 4 B | IEEE CRC32 over the preceding 1184 bytes |

CRC32 detects bit errors, missing bytes, extra bytes and frame shifts. A corrupt
frame is rejected before it can appear as false pressure or acceleration.

### 2.4 Teensy-to-PC path

The Teensy forwards valid binary frames through USB CDC. The Python reader
resynchronises on `ESK1`, validates CRC again, parses both matrices and all ACC
records, and keeps only the latest frame for display. Consequently:

- `source fps` is the real STM32 frame rate derived from sequence/timestamp;
- `display fps` is only the Matplotlib rendering rate and can be lower.

> 中文讲解：STM32负责采集和打包，Teensy负责提供SPI时钟、验证CRC并转USB；错误帧不会进入GUI。

## 3. Development and fault-isolation history

### 3.1 Foundation established by 31 July

| Observation | Isolation method | Root cause | Correction and result |
|---|---|---|---|
| SWD programming was unreliable | Reduced debug speed and connected under reset | Marginal SWD/reset contact and timing | DAPLink at 10 kHz with explicit STM32 target produced repeatable flashing |
| Teensy initially received `0x00` or unstable SPI data | Static GPIO mirror tests separated firmware from wiring | Host connector contact and mixed power-domain behaviour | Connector rework and controlled 3.3 V connection restored STM32–Teensy SPI |
| Output repeatedly fell to approximately 1 frame/s | Compared STM32 SPI state with Teensy USB behaviour | SPI3 RX state and blocking USB behaviour | Full-duplex SPI drain and reconnect-safe bridge restored approximately 25 frame/s in the standalone FSR system |
| Pressure appeared on incorrect rows | Injected known frames and checked sequence continuity | Payload marker was occasionally treated as a new frame | Fixed-width multi-frame sequence locking removed frame misalignment |
| Many complete FSR rows were intermittent | Flexing/reseating the FFC changed readings while digital transport remained valid | **Stage 9: FFC connector contact failure** | Connector was resoldered and replaced; widespread intermittent faults disappeared |
| A small number of fixed rows still failed | Direct resistance testing after MUX, ADC, SPI, USB and GUI passed | **Stage 10: FSR material/assembly itself** | Electronics were cleared; remaining lines were assigned to the replaceable FSR layer |
| GUI motion did not match physical motion | Moved pressure left/right and up/down on each side separately | FSR1 and FSR2 have different physical orientation | Independent transpose/reversal rules produced the correct physical display |
| Zero calibration showed pressure without load | Longer raw captures exposed drift, noise and invalid spans | Short calibration and cell-to-cell variability | Approximately 10-second captures and per-cell validation improved calibration without hiding hardware faults |

The 31 July work therefore established a critical diagnostic principle:
**transport, PCB electronics, connector and sensor material must be tested as
separate layers.**

> 中文讲解：7月31日前最重要的结论是第九阶段FFC连接器接触不良；更换connector后仍固定失效的行属于第十阶段FSR本体问题。

### 3.2 ACC bring-up after 31 July

The ACC bus was isolated with selectable single-device and slow static tests.

| Test | Purpose | Result |
|---|---|---|
| Decoder nCS continuity | Confirm exactly one active-low ACC selection | Decoder and OR-gate routes verified |
| Static MOSI high/low | Verify SDI path independently of SCK | MOSI path verified at exposed points |
| Slow SCK | Verify clock continuity with a multimeter/logic analyser | Shared SCK route verified |
| Repeated `WHO_AM_I` | Distinguish responding device from floating MISO | Valid devices returned `0x33`; absent/non-driving paths returned `0xFF`; low clamps returned `0x00` |
| Removal/exposed-pad test | Separate package failure from PCB routing | nCS, SCK and SDI remained correct without the devices |

A physical ACC3 SDO-to-nCS short was identified and repaired. ACC5's momentary
recovery and later data loss indicated intermittent LGA/package contact rather
than a decoder or common MOSI fault. The firmware was then changed to reject
all-`0x00`/all-`0xFF` axis payloads and periodically revalidate devices instead
of retaining a cached `OK` state.

An impossible diagnostic value (`MISO=1793`, where only 0 or 1 is valid) proved
that the original unprotected transport could accept corrupted but numerically
plausible payloads. This observation directly motivated the new CRC-protected
combined protocol.

> 中文讲解：ACC调试通过慢速nCS、MOSI、SCK和拆芯片测试排除了公共线路；发现过ACC3短路和LGA接触问题，同时证明旧协议需要CRC。

### 3.3 Combined single-module integration

The previous independent FSR and ACC programs were consolidated into one STM32
application and one Teensy bridge. The combined GUI was rebuilt to retain the
validated geometry:

- FSR panels use the hexagonal PCB outline and physical row/column orientation;
- ACC uses the mirrored 3 × 3 physical layout and 3D vectors;
- the operator can select FSR1, FSR2, ACC, or all views without changing the
  incoming protocol.

The first combined implementation produced approximately 9 source frame/s.
Initial speed work reduced MUX settling, raised ACC SPI, distributed identity
checks, and tested a faster Host link. This exposed the final transport issue.

### 3.4 Final blocker: two stale Host SPI bytes

After a speed update the GUI received no valid frames. The investigation was
performed in strict layers:

1. COM9 enumeration proved that the Teensy USB device was present.
2. HOST_IRQ counters proved STM32 requests reached Teensy GPIO2.
3. IRQ release counters proved each transaction completed.
4. The apparent onboard status LED was rejected as evidence because Teensy
   `LED_BUILTIN` and SPI SCK are both GPIO13; its flash was clock activity.
5. Magic/header/CRC counters showed progression from bad magic to valid header
   but failed CRC.
6. Raw prefix capture revealed a constant two-byte offset:

```text
stale byte 0 | stale byte 1 | 45 53 4B 31 | remaining ESK1 frame
```

The Teensy had clocked exactly 1188 bytes, so it received two stale bytes plus
only 1186 bytes of the logical frame. The final two CRC bytes were necessarily
missing.

Final correction:

- STM32 aborts and reinitialises SPI3 before publishing each frame, clearing
  stale peripheral state.
- Teensy searches for `ESK1` within the beginning of the same nCS transaction,
  discards any prefix, and continues clocking until one complete logical frame
  has been received.
- `#ESKDBG`, `#ESKFIRST`, `#ESKCRC` and `#ESKALIGN` diagnostics make IRQ,
  header, CRC and alignment failures directly observable.

With the paired firmware correction, the complete single-module system became
operational.

> 中文讲解：最终问题不是线路，而是每帧前多出两个SPI残留字节，导致最后两个CRC字节缺失。STM32清FIFO、Teensy自动寻找ESK1后解决。

## 4. Reusable bring-up workflow for the second module

The second module should not begin with the complete high-rate firmware. Use the
following order and preserve a result at every gate.

| Gate | Action | Pass criterion |
|---:|---|---|
| 1 | Inspect power rails, common ground, NRST and connector orientation | Stable 3.3 V; NRST high; no power-domain back-feed |
| 2 | Flash STM32 at 10 kHz under reset | Target detected and ELF verified |
| 3 | Run static MUX/SCK/MOSI/nCS GPIO tests | Correct voltage at MCU, connector and sensor endpoint |
| 4 | Test ADC1 and ADC2 independently with raw values | All AIN channels plausible; no fixed digital pattern |
| 5 | Scan FSR1 and FSR2 separately | Correct 16 × 16 matrices and physical direction |
| 6 | Test each ACC with repeated `WHO_AM_I` and register readback | `0x33`, `CTRL1=0x57`, `CTRL4=0x88` for fitted devices |
| 7 | Run a short Host SPI pattern frame | Stable magic/sequence before real sensor payload |
| 8 | Enable the 1188-byte combined frame at conservative Host speed | Increasing sequence, matching CRC, zero alignment drift |
| 9 | Confirm GUI mapping with isolated physical presses and board motion | Display location and vector direction match the hardware |
| 10 | Increase one frequency parameter at a time | CRC remains valid and analogue readings remain stable |

Do not recalibrate until connector contact, FSR assembly and resistor values are
final. A smaller FSR pull-down resistor remains an option if the response still
saturates too early; compare controlled no-load, medium-load and full-load raw
captures before changing it.

> 中文讲解：第二个模块必须按“供电→静态引脚→ADC→单独FSR→单独ACC→短帧→完整帧→GUI→提速”的顺序，不能直接上完整高速程序。

## 5. Next tasks

### Task 1 — Increase acquisition and bridge frequency

Start from the verified conservative baseline and change one parameter per
test. Record `source fps`, CRC failures, alignment prefix, FSR spatial accuracy
and ACC validity for at least 60 seconds.

| Step | FSR settle | ACC SPI | Host SPI | Target complete source rate |
|---|---:|---:|---:|---:|
| Stable baseline | verified conservative value | 500 kHz or verified fallback | 100–250 kHz verification | establish reference |
| Conservative increase | 100–50 us | 500 kHz–1 MHz | 250–500 kHz | 20–50 Hz |
| Higher-rate blocking test | 50–25 us | 1–2 MHz | 1–2 MHz | 40–80 Hz |
| Architecture upgrade | measured minimum | DMA/double buffer | 4–8 MHz | 80–150 Hz target |

Later improvements include timer-driven acquisition, DMA, double buffering,
independent FSR/ACC rates, and increasing the STM32 system clock only after all
prescalers and analogue settling delays are recalculated.

### Task 2 — Configure and validate the second module

Repeat the reusable bring-up workflow, maintain a separate module ID and test
record, and do not assume that calibration or physical mapping from module 1 is
transferable.

### Task 3 — Simulate two modules with one Teensy

Use separate nCS and HOST_IRQ inputs for each STM32 while sharing SCK/MOSI/MISO
only if the unselected module guarantees high-impedance MISO. The Teensy should
poll ready modules, attach a module ID to each validated frame, and forward an
interleaved USB stream. This test will establish whether one Teensy has adequate
SPI, RAM, USB and scheduling margin for two modules.

### Task 4 — Complete the mechanical module

Design the supporting frame, define connector strain relief and cable routing,
seal electronics where required, and inject silicone using controlled thickness,
alignment and curing conditions. Repeat zero/full calibration only after the
mechanical stack is final.

### Task 5 — Develop a scalable multi-module controller

One Teensy is unlikely to scale to many modules because of SPI scheduling, USB
bandwidth, connector count and power. USB power from a single uncontrolled port
is also insufficient without a measured system power budget.

Recommended control-board concept:

```text
E-SKIN module 1 ─→ Teensy/bridge 1 ─┐
E-SKIN module 2 ─→ Teensy/bridge 2 ─┤
E-SKIN module N ─→ Teensy/bridge N ─┤
                                    ↓
                     Powered hub / aggregation controller
                                    ↓
                       Ethernet interface → PC
```

The controller PCB should include:

- keyed connectors for each sensor module;
- sockets or board-to-board connectors for multiple Teensy bridges;
- protected USB-C or external power input with a defined power budget;
- dedicated regulated rails, per-module current measurement, fuses/load
  switches and controlled power sequencing;
- a powered USB hub or a controller with multiple USB-host interfaces;
- an Ethernet-capable aggregation processor or MCU;
- module ID, sequence, timestamp and CRC in every network packet;
- UDP for low-latency sensor streaming, with a reliable control/configuration
  channel where required.

A practical architecture is to let each Teensy retain responsibility for one or
two local modules, then use a central USB-host-capable processor to aggregate
their validated streams and forward them to the PC over Ethernet. The final
choice requires measured per-module power, achieved frame rate and total data
bandwidth.

> 中文讲解：多模块不建议让一个Teensy全部承担。更合理的是每个Teensy负责一到两个模块，总控PCB负责供电、USB汇聚、稳压保护和以太网转发。
